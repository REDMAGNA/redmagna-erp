# Guía de preparación: REDMAGNA ERP en Synology DS720+

**Estado:** instrucciones preparadas; aún no se ha instalado el proyecto en el NAS.

## Compatibilidad observada

Synology incluye el **DS720+** entre los modelos aplicables a Container Manager. Las capturas compartidas para este proyecto muestran DSM `7.2.1-69057 Update 12` instalado y DSM `7.4.1-90080` descargándose al 94%; no confirman que la instalación de DSM 7.4.1 haya terminado. Antes de continuar, confirma la versión en **Panel de control → Centro de información → General** y espera a que DSM complete el reinicio. La nota oficial de DSM 7.4.1 dice que la actualización reinicia el NAS, que no permite volver a una versión previa y que varios paquetes —incluido Container Manager— deben estar en versiones compatibles o actualizarse. Antes de aplicarla, revisa las instrucciones para el DS720+, compatibilidad de discos y paquetes instalados, y conserva una copia de seguridad recuperable de los datos y la configuración. ([notas oficiales DSM 7.4.1](https://www.synology.com/en-us/releaseNote/DSM?os=DSM&version=))

Synology publica Container Manager `24.0.2-1706` para DSM 7.4 e incluye el DS720+; esta versión requiere DSM 7.4 y su despliegue es gradual. Las notas identifican `24.0.2-1543` como la versión que agregó el comando `docker compose` al CLI y la hacen compatible con DSM 7.2.1 o posterior. Si el NAS sigue en DSM 7.2.1, confirma en Package Center que tenga una versión con CLI antes de usar las tareas de respaldo por terminal; para crear el proyecto, Container Manager también permite cargar `docker-compose.yml` desde su interfaz. No fuerces la instalación manual de un paquete incompatible. ([Container Manager para DSM 7.4 y modelos aplicables](https://www.synology.com/en-global/dsm/packages/ContainerManager?os_ver=7.4&search=docker), [notas de Container Manager para DS720+](https://www.synology.com/en-us/releaseNote/ContainerManager?model=DS720%2B&os=DSM&version=7_x_series), [Centro de descargas DS720+](https://www.synology.com/en-us/support/download/DS720%2B), [notas DSM para DS720+](https://www.synology.com/en-global/releaseNote/DSM?model=DS720%2B))

El DS720+ usa un Intel Celeron J4125 de cuatro núcleos y 64 bits; su memoria de fábrica es 2 GB y admite hasta 6 GB. Las imágenes base que usa este Compose (`python:3.12-slim` y `postgres:16-alpine`) están fijadas por digest de índice multi-arquitectura y publican variantes `linux/amd64`, compatibles con la arquitectura del NAS. Revisa la [auditoría de licencias y bases](auditoria-licencias-dependencias-v1.md) antes de actualizar un digest. Los 2 GB son un punto de partida ajustado porque DSM, PostgreSQL y la aplicación comparten memoria; por eso Compose inicia Gunicorn con `APP_WORKERS=1`. Tras ampliar al máximo compatible, se puede subir a dos procesos y observar memoria y espacio de intercambio. Esta es una recomendación operativa, no un mínimo oficial de Synology. ([Especificaciones DS720+](https://global.download.synology.com/download/Document/Hardware/DataSheet/DiskStation/20-year/DS720%2B/spn/Synology_DS720_Plus_Data_Sheet_spn.pdf), [arquitectura del CPU DS720+](https://kb.synology.com/de-de/DSM/tutorial/What_kind_of_CPU_does_my_NAS_have), [Python 3.12 slim en amd64](https://hub.docker.com/_/python/tags?name=3.12-slim), [PostgreSQL 16 Alpine en amd64](https://hub.docker.com/_/postgres/tags?name=16-alpine))

Synology documenta que Container Manager puede crear proyectos a partir de `docker-compose.yml`, asignando nombre y ruta de trabajo. Desde la vista del proyecto se construye y arranca la aplicación. ([Proyectos en Container Manager](https://kb.synology.com/index.php/es-mx/DSM/help/ContainerManager/docker_project?version=7))

## Estructura recomendada de carpetas compartidas

Crear cuatro carpetas compartidas en DSM. Restringe el acceso de personas a administradores y conserva el permiso de lectura/escritura del usuario de sistema **ContainerManager** en `docker/redmagna-erp`, que Container Manager necesita para leer el proyecto y construir la imagen:

| Carpeta compartida | Uso |
|---|---|
| `docker` | Código del proyecto y `docker-compose.yml`, en `redmagna-erp/` |
| `redmagna-db` | Archivos activos de PostgreSQL; no seleccionar para copia de archivos mientras el motor esté en ejecución |
| `redmagna-backups` | Exportaciones lógicas `.dump` que se respaldarán con Hyper Backup |
| `redmagna-media` | Fotos y PDF de evidencia de órdenes de trabajo, persistentes fuera del contenedor |

La configuración Compose utiliza rutas enlazadas del NAS. Esto deja la base fuera de la ruta del proyecto y permite respaldar los volcados lógicos sin copiar archivos vivos de PostgreSQL. Synology indica que los permisos asignados al volumen en Container Manager y los permisos de File Station deben permitir el mismo nivel de acceso. Usa un grupo DSM dedicado para el ERP y limita sus permisos a las carpetas de medios y respaldos; no concedas escritura a `Everyone`. La aplicación y el proceso de respaldo reciben el GID de ese grupo mediante `ERP_DATA_GID`. Synology recomienda usar Hyper Backup para carpetas/archivos enlazados a contenedores. ([Permisos de carpetas enlazadas](https://kb.synology.com/en-global/DSM/tutorial/Docker_container_cant_access_the_folder_or_file), [guía de respaldo de contenedores](https://kb.synology.com/en-global/DSM/tutorial/How_do_I_back_up_Docker_containers))

## Instalación

1. En DSM, verifica Package Center y el Centro de descargas del DS720+. Conserva una copia de seguridad de la configuración actual del NAS antes de actualizaciones mayores.
2. En File Station, extrae el paquete más reciente del ERP dentro de `docker`. La estructura resultante debe ser `/volume1/docker/redmagna-erp/docker-compose.yml` y debe contener las carpetas `server/` y `dist/`.
3. Duplica `.env.example` como `.env`. Si File Station no muestra archivos con punto inicial, activa la opción **Mostrar archivos ocultos**. Edita estas variables con las rutas de las carpetas compartidas y los datos de la red local:

   ```dotenv
   POSTGRES_DATA_PATH=/volume1/redmagna-db/redmagna-erp
   BACKUP_PATH=/volume1/redmagna-backups/redmagna-erp
   MEDIA_PATH=/volume1/redmagna-media/redmagna-erp
   DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,IP-LAN-DEL-NAS,nombre-local-del-nas
   ```

   Cambia `POSTGRES_PASSWORD` por un secreto aleatorio de al menos 24 caracteres y `DJANGO_SECRET_KEY` por otro secreto aleatorio distinto de al menos 50 caracteres. PostgreSQL rechazará la contraseña de ejemplo antes de crear su volumen, y la aplicación validará ambas claves antes de migrar. No compartas el `.env` ni lo incluyas en Git.

   Antes del primer arranque, crea en DSM las cuatro carpetas compartidas de la tabla y un grupo local dedicado `redmagna-erp`. Dentro de `redmagna-db`, `redmagna-backups` y `redmagna-media`, crea una subcarpeta `redmagna-erp`; usa esas rutas en `.env`. En **File Station → Propiedades → Permisos**, conserva lectura/escritura del usuario **ContainerManager** en el proyecto `/volume1/docker/redmagna-erp`; limita el acceso de personas a administradores. Da al grupo DSM dedicado acceso solo a las subcarpetas enlazadas de respaldos y medios. Obtén su GID numérico por SSH con `synogroup --get redmagna-erp` (habilita SSH temporalmente desde el Panel de control y vuelve a deshabilitarlo al terminar) y configúralo en `ERP_DATA_GID` en `.env`; no supongas que será `65534`. Compose agrega ese GID a la aplicación y al servicio que genera respaldos. La ruta de medios se monta en solo lectura en el respaldo y la de respaldos se monta en solo lectura en `db-restore-test`. Mantén el volumen de PostgreSQL accesible para Container Manager y el contenedor `db`, que inicializa y actualiza esos archivos. No amplíes permisos al resto de `docker`, a otras carpetas compartidas ni a `secrets/fiscal`; concede a esta última solo lectura para que la aplicación use el CSD. Si el proceso no puede escribir, revisa el GID, el ACL de DSM y los permisos de la subcarpeta antes de ampliar accesos.

   Redmagna confirmó que usa **Facturar en Línea (FEL Premium)**. `.env.example` deja `FEL_ENVIRONMENT=test` y credenciales vacías. Configura primero las credenciales de timbrado de pruebas; no agregues credenciales productivas hasta validar el flujo con el contador. La emisión productiva requiere cambiar el entorno y habilitar explícitamente `FEL_ALLOW_PRODUCTION=true`. La pantalla permite revisar CFDI de ingreso y Pagos 2.0, generar/descargar XML firmado y enviarlo explícitamente a FEL; antes de firmar un complemento de pagos confirma el resumen de facturas, saldos e IVA. Si la respuesta es incierta, consulta por referencia antes de intentar otro paso. Para habilitar el CSD, crea `/volume1/docker/redmagna-erp/secrets/fiscal/` con `redmagna.cer`, `redmagna.key` y `csd_password` (solo la contraseña, sin saltos de línea), configura `CFDI_CSD_HOST_PATH=/volume1/docker/redmagna-erp/secrets/fiscal` en `.env` y concede acceso de solo lectura a la carpeta y archivos al proceso de la aplicación (UID 65534 dentro del contenedor). Compose monta la carpeta en solo lectura. No copies estos archivos al paquete del código ni los adjuntes en mensajes. El IVA al 8% está deshabilitado por defecto. Solo configura `CFDI_ALLOW_BORDER_8_RATE=true` si Contabilidad confirmó el aviso SAT y que emisor y domicilio de expedición califican; cada concepto al 8% debe tener un producto enlazado, con su `ClaveProdServ` verificada y `sat_border_8_eligible` marcado en Django Admin. Cambiar la clave elimina esa marca. El ERP bloquea la clave genérica `01010101`, pero aún no comprueba automáticamente las marcas territoriales SAT ni el estatus del contribuyente. **No habilites cancelaciones hasta que Contabilidad valide el proceso y el WSDL de la cuenta:** FEL no ofrece sandbox para ese paso. La API requiere `FEL_ALLOW_CANCELLATION=true`, `FEL_ENVIRONMENT=production` y `FEL_ALLOW_PRODUCTION=true`, además de `FEL_CANCEL_PFX_BASE64` y `FEL_CANCEL_PFX_PASSWORD` con el PFX de cancelación del mismo CSD emisor. El archivo `.env` contendrá estos secretos; protégelo y nunca lo incluyas en Git ni en respaldos sin cifrar. Cada solicitud exige también confirmación dentro de la pantalla. La preparación coteja existencia de las claves en el XSD de catálogos CFDI local; no demuestra que la clave corresponda semánticamente al concepto. Antes de enviar, revisa RFC, vigencia del CSD, datos y claves SAT con Contabilidad. El XML se valida con el XSD SAT local; la clave de exportación `02` no se genera porque falta el Complemento de Comercio Exterior.
4. Antes de crear el proyecto, abre una terminal de DSM en el directorio del paquete y ejecuta `sh tools/preflight_synology.sh`. El verificador revisa que `.env` tenga secretos con la longitud mínima y distintos entre sí, que las rutas persistentes sean carpetas absolutas existentes y escribibles, que el GID sea numérico y que Compose acepte el archivo si el comando está disponible. No inicia contenedores ni muestra los valores secretos. Corrige todos los errores; los avisos requieren revisión manual en Container Manager o DSM. Después, en Container Manager, abre **Proyecto → Crear**. Usa `redmagna-erp` como nombre, `/volume1/docker/redmagna-erp` como ruta y el `docker-compose.yml` extraído como origen. Construye y arranca el proyecto.
5. Revisa los registros y el estado de salud de los contenedores `db` y `app`. La aplicación espera que PostgreSQL esté listo, aplica las migraciones, crea los grupos de acceso y arranca el servicio web. La comprobación `/healthz/` confirma que la aplicación también puede consultar la base.
6. En Container Manager, abre una terminal del contenedor `app` y ejecuta `python manage.py createsuperuser`. Entra después a `/admin/` para crear las cuentas de usuario y asignarlas a los grupos iniciales. Conserva el usuario administrador solo para administración del sistema.
7. Desde una computadora de la red local, abre `http://IP-LAN-DEL-NAS:8000/`, conecta el usuario y comprueba sus módulos. Cuando el contador entregue el plan de cuentas aprobado, entra a **Contabilidad → Catálogo contable y diarios** para crear cuentas y diarios; configura después **Automatización de pólizas** con las cuentas revisadas. No actives reglas con cuentas provisionales. Antes de capturar Gastos, Contabilidad debe crear categorías con cuentas de gasto aprobadas y configurar el diario de gastos, un diario de banco o caja para reembolsos, la cuenta de reembolsos pendientes y la cuenta de fondos de la empresa. Si se usa diario bancario, habilita conciliación en la cuenta bancaria asociada. El ERP no ejecuta transferencias: la persona que registra debe confirmar el pago ya efectuado; la póliza de salida se revisa, contabiliza y concilia por separado. `/admin/` queda disponible para administración y soporte técnico.
8. Abre `http://IP-LAN-DEL-NAS:8000/` para usar la pantalla conectada. Inicia sesión con el usuario del ERP; la pantalla aplica los permisos del grupo asignado y muestra enlaces a la licencia y a `/source.zip`.

Al actualizar desde una versión anterior, conserva primero un respaldo lógico de PostgreSQL y una copia cifrada de `.env`. No cambies la ruta de `POSTGRES_DATA_PATH` de una instalación existente. Si esa versión todavía no tiene `MEDIA_PATH`, crea su carpeta de medios dedicada, agrega al `.env` la ruta correspondiente y aplica permisos de escritura a esa carpeta enlazada; las variables nuevas no se agregan automáticamente al `.env` existente. Luego reemplaza los archivos del proyecto con la nueva versión y vuelve a construir/iniciar el proyecto desde Container Manager. Al iniciar, el contenedor aplica las migraciones de la base y sincroniza los permisos de los grupos. Comprueba el estado de salud, inicia sesión con un usuario de cada rol y confirma los módulos habilitados. No elimines ni cambies las rutas enlazadas de PostgreSQL, medios o respaldos durante una actualización.

Para facturar con estímulo fronterizo al 8%, no basta con `CFDI_ALLOW_BORDER_8_RATE=true`: agrega el código postal de expedición revisado en `CFDI_BORDER_8_REVIEWED_POSTAL_CODES` y marca en Django Admin cada producto cuya `ClaveProdServ` tenga la marca SAT aplicable. Configura la variable solo tras revisar aviso y elegibilidad con Contabilidad. El sistema bloquea el 8% si el código postal no está en la lista o si un concepto no tiene marca por producto.

### Acceso mediante HTTPS en Synology

Para mantenerlo solo en la red local, la configuración inicial puede usar el puerto 8000 por HTTP y acceso por VPN o LAN, sin redirección desde el router. Si vas a publicar el ERP detrás del proxy inverso HTTPS de DSM, configura un certificado y un nombre de dominio en DSM, y restringe el acceso de red al puerto del contenedor para que el proxy sea su única entrada. En `.env` usa el dominio en `DJANGO_ALLOWED_HOSTS` y configura:

```dotenv
APP_BIND_ADDRESS=127.0.0.1
APP_PORT=8000
DJANGO_CSRF_TRUSTED_ORIGINS=https://erp.tu-dominio.mx
DJANGO_USE_HTTPS_PROXY=true
DJANGO_SECURE_COOKIES=true
DJANGO_SECURE_SSL_REDIRECT=true
DJANGO_SECURE_HSTS_SECONDS=0
ERP_PUBLIC_URL=https://erp.tu-dominio.mx/
```

Sustituye el dominio por el de Redmagna y confirma en la configuración/prueba de DSM que el proxy envíe `X-Forwarded-Proto: https`. `APP_BIND_ADDRESS` limita la dirección del NAS a la que Compose publica el puerto; con `127.0.0.1`, DSM puede acceder desde el proxy local, mientras Gunicorn sigue escuchando en `0.0.0.0:8000` dentro del contenedor para recibir la conexión traducida por Docker. Los usuarios abren el dominio HTTPS de DSM; ya no entran directamente a `http://IP-LAN-DEL-NAS:8000/`. El arranque valida que las opciones de redirección, cookies y HSTS no se mezclen con una configuración de proxy incompleta. Deja HSTS en `0` al inicio; considera un tiempo mayor solo después de verificar HTTPS en todas las rutas y clientes. No reenvíes el puerto 8000 desde el router ni publiques el puerto de PostgreSQL.

## Copias de seguridad

El servicio `db-backup` exporta PostgreSQL en formato custom y guarda un archivo comprimido con las evidencias existentes. Primero escribe ambos archivos en un directorio temporal único, comprueba que el volcado se puede listar y que el archivo de medios se puede leer, y genera un manifiesto SHA-256 para el par. Publica los dos archivos y deja el manifiesto como marcador final; si falla la operación, retira los finales parciales de ese intento. Los nombres llevan un identificador: `redmagna-AAAAmmdd-HHMMSS-ID.dump`, `redmagna-media-AAAAmmdd-HHMMSS-ID.tar.gz` y `redmagna-checksums-AAAAmmdd-HHMMSS-ID.sha256`. La restauración valida ambos archivos antes de crear la base de prueba; los respaldos anteriores sin manifiesto se aceptan con aviso. SHA-256 detecta corrupción accidental, pero no demuestra autenticidad si alguien puede cambiar el respaldo y el manifiesto. Los servicios de respaldo y restauración usan el mismo digest PostgreSQL fijado que la base. Para automatizarlo, crea una tarea en **Panel de control → Programador de tareas → Tarea programada → Script definido por el usuario**, ejecutada con una cuenta administradora:

```sh
cd /volume1/docker/redmagna-erp
docker compose run --rm db-backup
```

La tarea crea los tres archivos con fecha en `/volume1/redmagna-backups/redmagna-erp`. En Hyper Backup selecciona `docker` (código y configuración) y `redmagna-backups` (base lógica y evidencia); excluye `redmagna-db`, que contiene los archivos activos del motor, y `redmagna-media`, cuya copia lógica se incluye en cada tarea. Conserva juntos el `.dump`, `.tar.gz` y `.sha256` con el mismo sello. Envía el respaldo a un destino distinto del NAS y habilita cifrado. Synology recomienda Hyper Backup para carpetas/archivos enlazados a contenedores. Los volcados, fotos, documentos y `.env` contienen información sensible de clientes y contabilidad.

La tarea de sistema usa el comando `docker compose`; confirma que Container Manager sea `24.0.2-1543` o posterior en DSM 7.2.1, o una versión compatible que ofrezca ese comando. El servicio `db-backup` lleva un perfil de mantenimiento y se puede ejecutar como servicio individual con Compose, sin iniciar los demás servicios de ese perfil. ([Notas oficiales de Container Manager para DS720+](https://www.synology.com/en-us/releaseNote/ContainerManager?model=DS720%2B&os=DSM&version=7_x_series), [perfiles de Compose](https://docs.docker.com/compose/how-tos/profiles/))

### Programar recordatorios comerciales por correo

En `.env`, configura `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` y `EMAIL_FROM` con los datos SMTP autorizados para Redmagna. Para STARTTLS usa `EMAIL_USE_TLS=true` y `EMAIL_USE_SSL=false` (normalmente puerto 587); para SSL directo usa `EMAIL_USE_TLS=false` y `EMAIL_USE_SSL=true` (normalmente puerto 465). SMTP envía avisos comerciales y permite recuperar contraseñas desde **¿Olvidaste tu contraseña?** en la pantalla de conexión. Define `ERP_PUBLIC_URL` como la dirección completa que los clientes pueden abrir para revisar y aceptar cotizaciones. Para la hoja comercial que se imprime o guarda como PDF, completa opcionalmente `ERP_COMPANY_NAME`, `ERP_COMPANY_LEGAL_NAME`, `ERP_COMPANY_RFC`, `ERP_COMPANY_ADDRESS`, `ERP_COMPANY_PHONE`, `ERP_COMPANY_EMAIL` y `ERP_COMPANY_WEBSITE` en `.env`; usa solo la razón social y RFC verificados. Después de cambiar estas variables, reinicia el servicio `app`; las cotizaciones abiertas desde entonces mostrarán esa cabecera. Una dirección local solo funciona para destinatarios en la red de la oficina; para clientes remotos, usa un dominio con HTTPS o acceso por VPN. Detrás del proxy inverso de DSM, configura `DJANGO_USE_HTTPS_PROXY=true` para que los enlaces de recuperación reconozcan HTTPS. No expongas directamente el puerto de la aplicación a Internet. El archivo `.env` vive dentro del proyecto en `docker`; limita la carpeta compartida `docker` a administradores, excluye `.env` del control de versiones y conserva una copia cifrada en el destino de respaldo protegido.

La ruta pública `/solicitar-cotizacion/` captura solicitudes en el CRM como oportunidades nuevas para revisión del equipo; no crea clientes ni cotizaciones automáticamente. Está desactivada por defecto. Antes de abrirla al público, confirma con Redmagna el texto final del consentimiento y el aviso de privacidad, publica ese aviso en una URL HTTPS, configura `ERP_PRIVACY_URL` y cambia `ERP_PUBLIC_LEADS_ENABLED=true` en `.env`; reinicia `app`. La verificación de arranque exige HTTPS mediante el proxy inverso DSM y `APP_BIND_ADDRESS=127.0.0.1` cuando la ruta se habilita. La protección incluye token temporal de formulario, campo trampa y un límite de tres solicitudes por hora por correo. Conserva el correo para dar seguimiento y un resumen HMAC para aplicar el límite; no almacena la dirección IP. El formulario no debe considerarse una defensa suficiente contra abuso distribuido.

Puedes etiquetar los enlaces de campaña con `utm_source`, `utm_medium` y `utm_campaign`, por ejemplo `/solicitar-cotizacion/?utm_source=buscador&utm_medium=anuncio&utm_campaign=instalacion`; esos valores se guardan en la oportunidad y aparecen en **Oportunidades → Rendimiento comercial → Campañas web**.

Para que Ventas reciba un aviso de cada prospecto nuevo, define `CRM_LEAD_NOTIFICATION_EMAIL` con un buzón interno válido. La creación del prospecto y el aviso pendiente se guardan en la misma transacción; el servicio `crm-reminders` intenta enviar la cola cada cinco minutos y reintenta errores SMTP hasta cinco veces. El estado, intentos y último error se consultan en `/admin/` → Ventas → Avisos de prospectos. Después de corregir SMTP, Administración puede seleccionar avisos agotados y elegir **Reintentar avisos fallidos seleccionados**; se conserva el contador de reintentos manuales. Si SMTP confirma el mensaje y la conexión se pierde antes de guardar el acuse local, un reintento podría duplicar el correo; la oportunidad permanece única. Si dejas vacía la variable, la captación sigue funcionando sin enviar avisos.

El servicio `crm-reminders` de Compose revisa cada cinco minutos la bandeja de avisos de soporte y las cotizaciones vencidas; si se activa, también envía los recordatorios del CRM. Configura SMTP en `.env`. Los avisos de respuestas de soporte se procesan automáticamente; para habilitar los recordatorios comerciales cambia `CRM_REMINDERS_ENABLED=false` a `CRM_REMINDERS_ENABLED=true` y ejecuta desde la carpeta del proyecto:

```sh
docker compose up -d crm-reminders
docker compose logs --tail=50 crm-reminders
```

El servicio espera a que la aplicación esté disponible. El CRM avisa una vez cuando una actividad entra en las siguientes 24 horas y una vez después de vencer. En soporte, cada respuesta del portal avisa al responsable activo o al creador si no hay responsable; la bandeja reintenta errores hasta cinco veces y deja el estado en `/admin/` y en la conversación del ticket. La entrega de correo puede repetirse si SMTP aceptó un mensaje y se perdió la confirmación. Si SMTP falla, el servicio reintenta en el siguiente ciclo según la espera registrada. Para desactivar los recordatorios CRM, cambia la variable a `false` y vuelve a ejecutar `docker compose up -d crm-reminders`; las notificaciones de soporte siguen activas mientras SMTP esté configurado.

### Recordatorios de cuentas por cobrar

La cobranza por correo está desactivada por defecto. Antes de habilitarla, revisa el correo de cada cliente y confirma con Redmagna quién debe recibir estados de cuenta. Después de configurar SMTP, define `BILLING_REMINDERS_ENABLED=true`; `BILLING_REMINDER_DAYS_AHEAD=3` envía un solo aviso cuando faltan hasta tres días naturales para vencer y otro cuando la factura ya venció. El servicio `crm-reminders` revisa la cola cada cinco minutos; actualízalo con `docker compose up -d crm-reminders`. Los avisos solo se generan para facturas abiertas o con pago parcial y saldo positivo. La fecha, el saldo mostrado, destinatario, intentos y resultado quedan en `/admin/` → Facturación → Recordatorios de facturas de cliente. Las facturas sin correo quedan omitidas en la cola. Los errores reintentan con espera creciente hasta cinco intentos; si se agotan, o si se omitieron por falta de correo, Contabilidad puede seleccionarlos en Django Admin y volver a ponerlos en cola, conservando el actor y la fecha del reintento. Si SMTP aceptó el mensaje pero se perdió la respuesta, el correo puede repetirse. La automatización no registra cobros, crea pólizas ni timbra/cancela CFDI. Para apagarla, vuelve a `BILLING_REMINDERS_ENABLED=false` y ejecuta de nuevo `docker compose up -d crm-reminders`.

La recepción de respuestas de clientes por IMAP es otro servicio opcional; no se activa al desplegar el ERP. En `.env`, configura `SUPPORT_IMAP_HOST`, `SUPPORT_IMAP_PORT` (993 para IMAP con TLS), `SUPPORT_IMAP_USERNAME`, `SUPPORT_IMAP_PASSWORD` y el buzón `SUPPORT_IMAP_MAILBOX`. Configura `SUPPORT_IMAP_AUTH_SERV_ID` con el identificador exacto que escribe el servidor de correo en `Authentication-Results`, después de retirar encabezados de autenticación aportados por remitentes externos. Si el proveedor no ofrece esa protección, no habilites el servicio. Es preferible usar un buzón dedicado y una regla del proveedor que dirija ahí las respuestas de tickets; el proceso conserva los mensajes en el servidor y no acepta adjuntos.

Tras probar el acceso con un mensaje de soporte controlado y verificar que el proveedor agrega un resultado DMARC confiable, activa el servicio desde la carpeta del proyecto:

```sh
docker compose --profile email-inbound up -d support-email-inbound
docker compose logs --tail=50 support-email-inbound
```

El servicio lee el buzón en modo de solo lectura cada cinco minutos; verifica folio en el asunto, correo registrado y `dmarc=pass`, y guarda solo el mensaje de texto admitido y metadatos de recepción. Los resultados ignorados/rechazados se registran y no vuelven a procesarse; revisa el motivo antes de cambiar datos o reenviar un correo. Para desactivarlo, ejecuta `docker compose stop support-email-inbound`; Compose lo deja apagado hasta que se vuelva a iniciar con el perfil `email-inbound`.

Antes de usar datos reales, hay que restaurar un `.dump` en una base de prueba y confirmar usuarios, cotizaciones y pólizas recuperadas. Si el ERP ya guarda evidencias, restaura el `.tar.gz` del mismo sello de tiempo en una carpeta aparte y verifica que puedes abrir sus archivos; no extraigas sobre la carpeta operativa. Por SSH, después de sustituir el sello por uno existente:

```sh
mkdir -p /volume1/redmagna-media-restore-test
tar -xzf /volume1/redmagna-backups/redmagna-erp/redmagna-media-AAAAmmdd-HHMMSS-ID.tar.gz -C /volume1/redmagna-media-restore-test
```

Mantén otra copia cifrada de `.env` y del código en un destino protegido; sin ellos no se reconstruye la configuración de la aplicación.

### Restaurar un respaldo en una base de prueba

En el Programador de tareas de DSM, crea una tarea manual de script definida por el usuario que se ejecute con la misma cuenta administradora. Cambia el nombre por un archivo `.dump` existente dentro de `/volume1/redmagna-backups/redmagna-erp`:

```sh
cd /volume1/docker/redmagna-erp
RESTORE_FILE=redmagna-AAAAmmdd-HHMMSS-ID.dump docker compose run --rm -e RESTORE_FILE db-restore-test
```

El servicio monta la carpeta en solo lectura, comprueba automáticamente el manifiesto del mismo sello y restaura en `redmagna_restore_test`. Si usas un respaldo anterior sin manifiesto, verás un aviso y se continuará sin la verificación SHA-256. No modifica `redmagna`; si el archivo no existe o el hash no coincide, la restauración falla, y si ya existe la base de prueba, también falla sin reemplazarla. Para restaurar medios, verifica antes el manifiesto desde la carpeta de respaldos con `sha256sum -c redmagna-checksums-AAAAmmdd-HHMMSS-ID.sha256` y extrae el archivo `redmagna-media-AAAAmmdd-HHMMSS-ID.tar.gz` a una carpeta aparte. Para inspeccionar la base, abre la terminal del contenedor `db` y ejecuta `psql -U redmagna -d redmagna_restore_test`. Revisa al menos un usuario, una cotización y una póliza. Conserva esta base de prueba solo mientras sea necesaria; para eliminarla, confirma cuidadosamente el nombre y ejecuta `dropdb -U redmagna redmagna_restore_test` desde la terminal del contenedor `db`.

## Reglas de operación del proyecto

- Usa **Detener/Iniciar** para mantenimiento normal.
- No uses **Limpiar** o **Eliminar** como mecanismo de reinicio. La documentación de Synology indica que **Limpiar** ejecuta `docker-compose down` y elimina contenedores, redes, volúmenes e imágenes del proyecto. La carpeta enlazada de PostgreSQL es externa al proyecto, pero hay que verificar la ruta del NAS antes de borrar un proyecto. ([Operaciones de proyecto de Container Manager](https://kb.synology.com/index.php/es-mx/DSM/help/ContainerManager/docker_project?version=7))
- No publiques el puerto 8000 en Internet. Para acceso remoto se debe configurar VPN o proxy HTTPS y revisar firewall/contraseñas.
- Si se abre `dist/index.html` directamente, funciona con datos locales de demostración. Para operar con la base central debe usarse la pantalla desde `http://IP-LAN-DEL-NAS:8000/`. La integración de envío requiere configurar credenciales sandbox y validarse con el contador de Redmagna antes de usarla para documentos reales.

## Alcance de esta guía

La imagen web se ejecuta con un usuario sin privilegios de administrador, usa un sistema de archivos raíz de solo lectura y monta `/tmp` como espacio temporal en memoria; los archivos durables se guardan en el volumen de medios. Docker Compose espera a PostgreSQL antes de iniciar la aplicación. Esta guía se basa en la compatibilidad de paquete publicada por Synology y en el Compose actual del proyecto. No demuestra que la instalación ya corra en el DS720+: queda pendiente ejecutar el despliegue, crear la cuenta, revisar registros, realizar una cotización de prueba y probar restauración de respaldo antes de cargar información productiva.
