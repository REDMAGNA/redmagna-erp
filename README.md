# REDMAGNA ERP — prototipo y núcleo inicial

Proyecto abierto en construcción para ventas, operaciones y administración financiera de Redmagna. Incluye un prototipo visual y un servicio web inicial con PostgreSQL para clientes, cotizaciones, órdenes de venta, órdenes de trabajo, cuentas por cobrar, cobros y pólizas manuales.

## Licencia

El proyecto usa GNU AGPL versión 3 solamente (`AGPL-3.0-only`); [LICENSE](LICENSE) contiene el texto íntegro. La pantalla conectada muestra enlaces a la licencia y al paquete del código fuente (`/source.zip`), conforme a la sección 13. La [auditoría de dependencias](docs/auditoria-licencias-dependencias-v1.md) enlaza el SBOM de ruedas Python bloqueadas; aún faltan la revisión de avisos nativos y el inventario de las imágenes finales antes de publicar un release.

## Desarrollo abierto

El proyecto sigue en desarrollo y aún no es un release estable. Consulta el [registro de cambios](CHANGELOG.md) y la [política de seguridad](SECURITY.md). Los problemas de seguridad deben reportarse en privado; no publiques vulnerabilidades ni secretos en issues públicos.

Para crear un paquete versionado para Synology y regenerar el archivo de código fuente AGPL, ejecuta desde la raíz del proyecto con Python 3.9 o posterior. Los empaquetadores excluyen `.env` locales, carpetas `secrets/`, certificados y llaves privadas; el paquete verifica esa exclusión antes de guardarse:

```sh
python tools/package_synology.py --output-dir ../redmagna-erp-build
```

La carpeta de salida debe estar fuera del proyecto. El paquete excluye el entorno virtual y los archivos `.env`.

## Incluye

- Guía de despliegue para Synology DS720+ y verificador `sh tools/preflight_synology.sh`, que revisa rutas, secretos y configuración Compose sin iniciar contenedores.
- Pantalla web conectada al servicio cuando se abre desde el servidor, con inicio mediante token y permisos por rol.
- Sesiones API separadas por navegador; el servidor guarda el hash del token, permite revisar y revocar otros navegadores desde el panel Sesiones, y ofrece a Administración una lista global y revocación individual en Django Admin y `/api/auth/sessions/`. Cambiar la contraseña o desactivar una cuenta revoca sus sesiones activas.
- Panel de resumen para cotizaciones, cuentas por cobrar, proyectos y clientes.
- Directorio de clientes con datos comerciales y fiscales básicos.
- Varios contactos comerciales por cliente con área/puesto, correo y teléfono; conserva el historial mediante archivado y permite señalar un contacto principal.
- Creación de cotizaciones con equipos, materiales, instalación y servicios, descuentos porcentuales de 0 a 100 por concepto, e IVA calculado por concepto sobre el subtotal neto; los descuentos y las tasas de IVA por renglón se conservan al aceptar cantidades parciales, facturar internamente y preparar el CFDI. Las plantillas internas pueden precargar conceptos, vigencia, tasa comercial y notas, con copia histórica independiente para cada propuesta. El cliente puede aceptar cantidades parciales por concepto desde el enlace público; el sistema recalcula el importe, valida las cantidades en el servidor y limita requerimientos de inventario y facturación a las cantidades aceptadas.
- Política opcional de descuentos excepcionales, apagada por defecto y sin límite comercial precargado: Gerencia configura el máximo en Django Admin, ve el porcentaje que solicita la cotización y el límite vigente, autoriza las que lo superan y consulta el registro de autorizaciones. La aprobación queda ligada a los conceptos revisados; si la política está habilitada, el cliente no puede aceptar una cotización que siga pendiente de autorización.
- Plazo de pago predeterminado opcional por cliente, copiado a cada cotización como condición comercial; al preparar la cuenta por cobrar se calcula un único vencimiento desde la fecha de emisión, editable por Contabilidad en el borrador.
- Administración de plantillas de cotización en `/api/quote-templates/`; admite archivo lógico y bitácora de cambios, sin borrar plantillas que ya se usaron.
- Revisión versionada de cotizaciones enviadas: conserva la versión anterior, crea un nuevo borrador y registra el cambio con actor y fecha.
- Vínculo opcional de conceptos a productos/servicios del catálogo, conservado hasta la factura interna.
- Vista imprimible de cotizaciones para compartir con clientes o guardar como PDF desde el navegador.
- Aprobación de cotizaciones para generar proyectos de trabajo.
- Agenda semanal de órdenes de servicio programadas con horario, cliente, folio y responsable; no calcula disponibilidad ni capacidad de técnicos.
- Preparación de ventas para capturar su facturación en FEL.
- Recordatorios opcionales por correo para facturas próximas a vencer y vencidas; se registran por factura y etapa, y solo se activan tras configurar SMTP y `BILLING_REMINDERS_ENABLED=true`.
- Proveedor FEL Premium confirmado por Redmagna; genera CFDI 4.0 de ingreso y Pagos 2.0 firmados en local, y permite envío, consulta y recuperación segura por referencia.
- Facturas internas de cobranza y estados de cuenta de cliente imprimibles (identificados como documentos internos), y aplicación de cobros a cuentas por cobrar.
- Antigüedad de saldos por cobrar con fecha de corte, bandas de vencimiento y detalle por cliente/factura. Exporta el detalle y el estado de cuenta del cliente a CSV seguro para hoja de cálculo.
- Antigüedad de cuentas por pagar por proveedor y estados de cuenta descargables a CSV seguro para hoja de cálculo.
- Conciliación de auxiliares CxC/CxP contra las cuentas de control del mayor a una fecha; muestra diferencias y permite exportar el resultado a CSV.
- Apertura auxiliar CxC/CxP desde CSV con lote persistente, huella e idempotencia, reserva de referencias externas y revisión obligatoria por otra persona; se publica sin duplicar pólizas y queda como saldo operativo, sin habilitar Pagos 2.0 para historia fiscal incompleta.
- Estado de cuenta de cliente con cargos, cobros aplicados y saldo acumulado a una fecha de corte.
- Estado de cuenta de proveedor con facturas, pagos aplicados y saldo acumulado al corte.
- Pólizas contables manuales de doble partida.
- Balanza de comprobación por periodo con apertura, movimientos y cierre de pólizas contabilizadas.
- Cierres mensuales contables: bloquean nuevas contabilizaciones en meses cerrados, impiden cerrar con pólizas borrador y guardan en bitácora quién cerró o reabrió y por qué.
- Libro mayor por cuenta con detalle de pólizas contabilizadas, saldos de apertura, movimientos y saldo acumulado.
- Estado preliminar de resultados y balance general basados en el libro contabilizado y la clasificación del catálogo.
- Conciliación bancaria mediante importación CSV, sugerencias ordenadas por cuenta, importe, referencia y fecha, vínculo revisado a pólizas y cierre con historial inmutable.
- Inventario sin valuación contable, con ubicaciones administrables, traspasos auditables, recepciones de compra, reservas por cantidad y número de serie, destinos de surtido, reabastecimiento por ubicación y conteos físicos con revisión separada y bloqueo por saldos desactualizados; el registro de equipos se busca y pagina, y muestra orden, proveedor y fecha de recepción cuando existe ese origen.
- Listas de verificación por orden de trabajo, con registro de quién completó cada punto y cierre bloqueado hasta completar toda la lista y agregar nota.
- Plantillas reutilizables de listas de verificación; al aplicarlas, los puntos se copian a la orden y conservan su contenido aunque después cambie la plantilla.
- Ubicación de servicio y contacto del sitio por orden de trabajo, separados de los datos fiscales del cliente; los cambios quedan auditados y el sitio se congela al registrar la conformidad.
- Catálogo de sitios reutilizables por cliente; Ventas puede fijar el sitio en la cotización, que se muestra al cliente y se copia a la orden aprobada. La cotización y cada orden conservan el nombre, domicilio y contacto como snapshots históricos.
- Acuse operativo de conformidad del cliente capturado por personal de Redmagna y ligado a la orden de trabajo; no es firma electrónica certificada.
- Tickets de soporte vinculados a clientes, órdenes de trabajo y equipos instalados por serie, con prioridad, asignación, estados auditados, SLA opcionales y notas internas inmutables.
- Evidencia privada de instalación y soporte: fotos JPG/PNG/WEBP y PDF ligados a la orden, con autor, fecha, descripción, validación de contenido y descarga con permisos.
- Compras iniciales con proveedores, precios y plazos de entrega por producto, órdenes con costo de referencia editable y recepción estimada, RFQ enviadas por SMTP con historial de intento y resultado, comparación de ofertas recibidas, recepciones parciales, facturas contra lo recibido, pagos parciales y pólizas borrador configurables; los pagos aplicados se pueden revertir con motivo y reversa contable cuando exista una póliza contabilizada.
- La adjudicación de compras puede repartir cantidades de un mismo producto entre ofertas de distintos proveedores; cada renglón conserva su solicitud y oferta de origen, la solicitud mantiene el saldo pendiente y se crean órdenes borrador independientes. Si Compras elige un precio mayor que otra oferta vigente disponible, registra una justificación inmutable.
- Acuerdos marco de compra disponibles en la pantalla de Compras, `/api/purchasing/framework-agreements/` y Django Admin: guardan proveedor, fechas, productos y precios; cada límite de cantidad es opcional y se permite un renglón por producto para que el límite sea inequívoco. Tras activar un acuerdo, sus condiciones quedan inmutables. Compras puede generar órdenes borrador dentro de la vigencia; el sistema reserva el saldo, impide superar el límite incluso con solicitudes concurrentes y libera el saldo si se cancela la orden.
- Gastos internos en MXN con comprobantes, aprobación, póliza, registro de reembolsos ya pagados, parcialidades y reversa auditada; la salida bancaria debe revisarse y conciliarse, y no se determina IVA acreditable.
- Gastos internos con comprobantes privados JPG/PNG/WEBP/PDF, reportes por persona, aprobación o rechazo con motivo y preparación manual de póliza borrador; categorías y cuentas se configuran con el catálogo autorizado por Contabilidad. El ERP no inicia la transferencia y no determina IVA acreditable.
- Antigüedad de cuentas por pagar por proveedor, con fecha de corte y bandas de vencimiento capturado.
- Solicitud pública de cotización desactivada por defecto, con creación de prospectos CRM, consentimiento y atribución UTM; su activación exige aviso de privacidad HTTPS y proxy inverso configurado.
- Administración puede revisar el momento de consentimiento del prospecto en su ficha, y buscar oportunidades por UTM y campaña.
- Aviso interno opcional de nuevos prospectos por SMTP; la cola conserva pendientes y reintenta envíos, sin perder oportunidades si el correo falla.
- Administración puede volver a programar un aviso fallido al corregir la conexión de correo.
- Preparación de snapshots fiscales revisables; el XML firmado no se timbra hasta que Contabilidad lo envía expresamente a FEL.

## Cómo abrirlo

### Prototipo visual

Abre `dist/index.html` para recorrer los datos ficticios de demostración; esos cambios se guardan solo en el navegador. Al desplegar el servicio, entra en `http://<NAS>:8000/` para usar la pantalla conectada a la API con el botón **Conectar al ERP**. Así la pantalla comparte el mismo origen y usa los permisos del usuario autenticado.

### Servicio inicial en Docker

1. Copia `.env.example` como `.env`, reemplaza ambas claves por valores largos y aleatorios y define las rutas persistentes del host. Para preparar snapshots fiscales, completa los datos del emisor `CFDI_ISSUER_*`; no ingreses ahí contraseñas ni llaves privadas. Para Synology, sigue la [guía del DS720+](docs/guia-synology-ds720-redmagna-erp.md).
2. En Docker Compose, inicia el proyecto con `docker compose up --build`. La imagen instala `server/requirements.lock`, con versiones y hashes de dependencias para ruedas binarias. PostgreSQL rechaza la contraseña de muestra antes de inicializar su volumen; la aplicación también valida ambas claves y la configuración básica de seguridad antes de aplicar migraciones versionadas y preparar grupos de acceso. El servicio web corre sin privilegios de root y con raíz de archivos de solo lectura; `/tmp` usa memoria temporal y los archivos persistentes van al volumen de medios. `/healthz/` comprueba la conexión a PostgreSQL.
3. Crea la cuenta administradora con `docker compose exec app python manage.py createsuperuser`.
4. El servicio queda disponible en el puerto 8000. Entra a `http://<NAS>:8000/` y usa **Conectar al ERP**; cada inicio crea una sesión API independiente, con vencimiento predeterminado de 12 horas y un token guardado solo en la sesión de esa pestaña. La migración conserva la vigencia de los tokens existentes y sustituye su almacenamiento por hashes. Puedes ajustar el vencimiento con `ERP_API_TOKEN_TTL_HOURS` (mínimo 1 hora); al expirar, la pantalla borra el token y pide volver a conectar. El enlace **¿Olvidaste tu contraseña?** lleva a `/accounts/password-reset/`; requiere configurar SMTP (`EMAIL_*`) para enviar las instrucciones y devuelve el mismo mensaje tanto si el usuario existe como si no. Salir revoca solo la sesión actual con `POST /api/auth/logout/`; cambiar la contraseña o desactivar la cuenta revoca sus sesiones activas. `/api/auth/sessions/` lista las sesiones propias; el grupo Administración puede consultar todas y revocar una por una con `POST /api/auth/sessions/{id}/revoke/`. También se pueden revisar y revocar desde `/admin/` → Accesos y sesiones. La API expone `/api/auth/token/`, `/api/auth/me/`, `/api/auth/logout/` y las rutas de sesiones, y filtra las acciones de la interfaz por permisos de usuario. Las rutas iniciales son `/api/customers/`, `/api/quotes/` y `/api/work-orders/`.

El proceso web usa un solo worker por defecto (`APP_WORKERS=1`) para limitar el consumo de memoria en el DS720+ con 2 GB. Si el NAS se amplía, aumenta el valor gradualmente y observa memoria y espacio de intercambio.

Para acceso HTTPS con el proxy inverso de DSM, limita la publicación del puerto del NAS con `APP_BIND_ADDRESS=127.0.0.1` y configura las variables `DJANGO_USE_HTTPS_PROXY`, `DJANGO_SECURE_COOKIES`, `DJANGO_SECURE_SSL_REDIRECT` y `DJANGO_CSRF_TRUSTED_ORIGINS` según la [guía de Synology](docs/guia-synology-ds720-redmagna-erp.md). Este valor limita el puerto publicado por Compose; Gunicorn sigue escuchando en `0.0.0.0:8000` dentro del contenedor para que la traducción de puertos de Docker funcione. El arranque verifica que Django confíe en `X-Forwarded-Proto` solo cuando el puerto del NAS está enlazado a localhost.

Las cotizaciones pueden seleccionar un contacto activo del cliente como destinatario; su nombre y correo se copian a la propuesta y se conservan en revisiones. Sin selección se usa el correo del cliente. El correo y la aceptación pública utilizan el destinatario guardado. Las acciones `send`, `send-email`, `approve` y `cancel` administran su ciclo; enviar por correo requiere SMTP y `ERP_PUBLIC_URL` configurados. El enlace firmado permite al cliente revisar los conceptos, aceptar cantidades parciales por renglón y ver el importe recalculado antes de confirmar nombre y correo; el servidor limita cada cantidad a lo propuesto y a tres decimales; la aceptación crea una orden de venta y una orden de trabajo en una transacción y conserva un registro inmutable con nombre, correo y fecha. Se exige el correo registrado, se impide duplicar la aceptación y se invalida el enlace si la cotización se reemplaza, vence o se canceló. Es una aceptación comercial, no una firma electrónica certificada. La hoja de cotización que se imprime o guarda como PDF usa la cabecera configurable `ERP_COMPANY_*`; completa razón social, RFC y contacto solo con datos confirmados en `.env`. Operaciones puede agregar puntos con `POST /api/work-orders/{id}/checklist/add/` (`label`) y marcar o reabrir cada uno con `PATCH /api/work-orders/{id}/checklist/{item_id}/` (`is_completed`). Cuando la orden está en curso, tiene nota de cierre y checklist completo, Operaciones puede registrar el acuse del cliente con `POST /api/work-orders/{id}/customer-acceptance/` (nombre, correo opcional, observaciones y confirmación explícita). El registro inmutable identifica también al trabajador que lo capturó; no es una firma electrónica certificada y no es requisito obligatorio para terminar el servicio. Desde la orden, Operaciones carga evidencia con `POST /api/work-orders/{id}/evidence/` como `multipart/form-data` (campo `file`, descripción opcional); acepta fotos JPG/PNG/WEBP y PDF hasta 10 MB. Gerencia, Operaciones, Ventas, Contabilidad y Almacén pueden consultar y descargar según sus permisos; los archivos no se publican como medios estáticos. El cierre por `/api/work-orders/{id}/transition/` exige una nota y todos los puntos completados; al cerrar, la lista queda bloqueada.

El módulo **Gastos** está disponible desde la navegación al conectar un usuario con permisos. La persona captura sus gastos en MXN, adjunta comprobantes de hasta 10 MB y agrupa los gastos libres en un reporte; el servidor exige comprobante según la categoría y limita la consulta al responsable salvo permisos globales. Gerencia aprueba o rechaza con motivo y no puede aprobar su propio reporte. Contabilidad administra categorías y cuentas; después de aprobar un reporte, puede crear una póliza borrador balanceada desde `/api/expenses/reports/{id}/prepare-journal/`. Los gastos pagados por la persona se abonan a la cuenta de pasivo configurada; los pagados por la empresa se abonan a la cuenta de fondos configurada. La póliza queda sin contabilizar para revisión. Cuando ya se contabiliza, Contabilidad puede registrar un reembolso parcial o total que ya ocurrió, con transferencia/cheque/caja, referencia y confirmación explícita; genera una póliza de salida en borrador y protege contra reintentos duplicados. La conciliación bancaria es un paso separado. El reembolso se puede revertir con confirmación del retorno/cancelación del pago y motivo, lo que crea una póliza inversa contabilizada; antes de revertir el gasto original deben revertirse sus reembolsos activos.

Si el cliente solicita cambios después del envío, `POST /api/quotes/{id}/revise/` crea una nueva cotización borrador con los conceptos y precios copiados, aumenta el número de revisión, marca la anterior como reemplazada y agrega eventos de auditoría para ambas. La anterior permanece consultable e inmutable. El reintento sobre una versión reemplazada sigue su cadena hasta devolver la revisión más reciente, incluso si la primera revisión también fue reemplazada. La API devuelve `revision_of_number` y la lista muestra el folio de origen de cada revisión. En la interfaz, crear una revisión abre ese borrador en el formulario para editarlo; desde la lista se pueden reabrir los borradores con `sales.change_quote`. El perfil de Gerencia incluye ese permiso para completar el flujo de revisión.

Gerencia y Operaciones pueden programar inicio/fin, asignar un usuario activo y guardar notas de ejecución desde la pantalla; la API usa `PATCH /api/work-orders/{id}/schedule/`. `GET /api/work-orders/assignees/` muestra usuarios activos solo a quienes tienen permiso para programar. Operaciones registra horas y actividad durante trabajos en curso mediante `POST /api/work-orders/{id}/log-hours/`; las entradas son inmutables. El reporte `GET /api/work-orders/hours-report/?date_from=AAAA-MM-DD&date_to=AAAA-MM-DD` resume horas por servicio y persona para periodos de hasta un año; las horas son seguimiento operativo y no calculan nómina ni costos. Las órdenes muestran también un resumen de venta aceptada con IVA, pendiente de facturar, facturas internas, borradores y saldo de cuentas por cobrar; no calcula costos ni margen, y las facturas internas no confirman el timbrado CFDI. La hora de fin debe ser posterior a la de inicio; terminar la orden requiere una nota de cierre, y las órdenes terminadas o canceladas ya no se pueden reprogramar.

El inventario usa `/api/inventory/products/`, `/api/inventory/locations/`, `/api/inventory/balances/`, `/api/inventory/movements/`, `/api/inventory/transfers/` y `/api/inventory/units/`. Almacén administra productos sin precios ni costos y puede elegir seguimiento por cantidad o por número de serie; no se puede cambiar el método de seguimiento tras crear historial. Registra entradas con `POST /api/inventory/movements/receive/`, salidas a órdenes con `/issue/`, devoluciones con `/return/` y ajustes con `/adjust/` (dirección `in` u `out`). Las acciones manuales de movimiento requieren `idempotency_key`: la primera creación responde 201, un reintento igual responde 200 con el registro existente y la misma clave con datos distintos se rechaza. Toda entrada requiere una `reference` de origen; recepciones de compra guardan el número de orden y las entradas manuales deben indicar su remisión u otro respaldo. Devoluciones y ajustes exigen describir el motivo en `note`; el servidor y la interfaz rechazan el movimiento si falta el dato requerido. Para artículos serializados, la cantidad debe ser entera y coincidir con las series indicadas; cada equipo puede apartarse con `POST /api/inventory/units/{id}/reserve/` para una orden programada o en curso, liberarse mediante `/release/` o entregarse solo a la orden que tenga la reserva. Una devolución debe llevar la misma serie y los traspasos cambian su ubicación preservando el historial; cada traspaso también requiere un motivo en `note`. Cuando la orden termina, `POST /api/inventory/units/{id}/install/` registra cliente, fecha de instalación y vencimiento opcional de garantía. `POST /api/inventory/transfers/` traslada uno o más productos entre ubicaciones activas en una transacción y admite reintentos con la misma `idempotency_key`. La consulta `GET /api/inventory/reorder-rules/{id}/forecast/?horizon_days=30` proyecta hasta 180 días de entradas esperadas y trabajo programado; marca compromisos que carecen de fecha o ubicación. No permite existencias negativas. Las órdenes de trabajo muestran sus materiales recientes y quedan enlazadas a las salidas y devoluciones. El alcance y sus límites están en [inventario básico de Redmagna](docs/inventario-redmagna-v1.md).

Compras registra proveedores y condiciones comerciales por producto en `/api/purchasing/supplier-products/`; cada alta o cambio queda como revisión inmutable con actor, fecha, valores y motivo, y la edición exige justificar el cambio. La consulta de costos usa el permiso separado `purchasing.view_supplierproduct`. Al preparar órdenes, propone el costo vigente editable y la fecha esperada con base en los plazos de cada producto. Las órdenes conservan su costo cuando cambia el catálogo. Crea borradores con conceptos de inventario en `POST /api/purchasing/orders/`, solicita la compra mediante `/confirm/` y registra recepciones parciales en `/receive/`, con una ubicación por renglón. Cada recepción se liga a un movimiento de inventario y usa una clave idempotente para evitar duplicados por reintento. Contabilidad puede registrar facturas de proveedor ligadas a órdenes recibidas mediante `POST /api/purchasing/orders/{id}/register-bill/`; el control impide volver a facturar más unidades de las recibidas y detecta folios repetidos por proveedor. La fecha de vencimiento se captura opcionalmente desde la factura recibida, sin imponer términos comerciales; `GET /api/purchasing/supplier-bills/payables-aging/?as_of=AAAA-MM-DD` agrupa los saldos pendientes por vencimiento y muestra su detalle por proveedor. Los pagos se capturan en borrador en `/api/purchasing/supplier-payments/` y se aplican con `POST /api/purchasing/supplier-payments/{id}/post/`; el saldo de cada factura se recalcula con las aplicaciones registradas y admite pagos parciales. Si Contabilidad activa las reglas respectivas con cuentas/diarios revisados, la captura de factura y la aplicación del pago generan pólizas borrador que deben contabilizarse manualmente. Se puede adjuntar un XML CFDI 4.0 en `POST /api/purchasing/supplier-bills/{id}/attach-cfdi/`; el sistema valida su estructura local con el XSD base disponible, coteja emisor, receptor, UUID, fecha, folio e importes con la cuenta por pagar y evita asociar el UUID más de una vez. El XML queda privado y solo se descarga con permiso de consulta. Esta revisión no verifica criptográficamente los sellos ni consulta en el SAT el estado del UUID; descuentos, retenciones, moneda extranjera y casos fiscales distintos requieren soporte antes de usar esta captura. La cuenta por pagar tampoco registra pagos no aplicados ni concilia bancos. Las RFQ se envían desde `/api/purchasing/sourcing/{id}/send-rfq/` a un proveedor activo con correo registrado; el mensaje no es una orden de compra. Las respuestas se capturan manualmente en `/api/purchasing/sourcing/{id}/offers/`. El envío requiere SMTP configurado y el permiso `purchasing.send_purchasingsourcingrequest`. El detalle y permisos están en [compras, proveedores y recepciones](docs/compras-proveedores-recepciones-v1.md).

Desde que una orden de trabajo está programada y mientras siga activa, Ventas puede preparar borradores de factura de avance con `POST /api/work-orders/{id}/create-invoice/`; las órdenes canceladas quedan bloqueadas. Cada renglón acepta `quote_line` y `quantity`; omitir la lista factura todo el saldo pendiente. El ERP muestra cantidades cotizadas, facturadas y pendientes, conserva el vínculo entre cada renglón de factura y su concepto de cotización, y no permite exceder la cantidad cotizada sumando todas las facturas de la orden. Al facturar el saldo completo, no se ofrece otra factura. Contabilidad revisa cada borrador antes de abrir la cuenta por cobrar.

La facturación interna está disponible en `/api/billing/invoices/` y los cobros en `/api/billing/payments/`. Las facturas se capturan en borrador con conceptos y se abren mediante `POST /api/billing/invoices/{id}/open/`. Los cobros se capturan con sus aplicaciones y se registran mediante `POST /api/billing/payments/{id}/post/`; por ahora el importe debe quedar aplicado completamente a facturas abiertas del mismo cliente y moneda; no se registran anticipos ni cobros sin aplicar. El diseño para anticipos está separado en la documentación fiscal y requiere definir el tratamiento con el contador antes de activarse. Contabilidad puede preparar un snapshot para revisión con `POST /api/billing/invoices/{id}/prepare-cfdi/`; requiere datos fiscales del emisor en `.env`, datos completos del receptor, la clave de exportación y clasificación SAT por concepto. La preparación coteja las claves con las enumeraciones del XSD de catálogos CFDI 4.0 incluido; una clave existente no garantiza que sea semánticamente adecuada para la operación. El 8% permanece bloqueado salvo que Contabilidad valide la elegibilidad del emisor y conceptos y configure `CFDI_ALLOW_BORDER_8_RATE=true`; además, cada producto debe marcarse como elegible en Django Admin después de revisar su clave SAT, y cambiar esa clave elimina la marca. La aplicación también rechaza a esa tasa la clave genérica `01010101`, pero no verifica automáticamente el aviso ni la región fronteriza del emisor. Para generar y firmar localmente un CFDI de ingreso preparado, configura `CFDI_CSD_HOST_PATH` con los archivos protegidos `redmagna.cer`, `redmagna.key` y `csd_password`, y llama `POST /api/billing/fiscal-documents/{id}/generate-xml/`; devuelve el XML firmado y lo valida con XSD SAT local. El envío explícito a FEL Premium usa `POST /api/billing/fiscal-documents/{id}/send/`, requiere credenciales FEL, guarda una referencia idempotente y conserva como pendiente cualquier resultado de transporte incierto para consultar primero con `POST /api/billing/fiscal-documents/{id}/query/`. `FEL_ENVIRONMENT` es `test` por defecto; producción requiere además habilitar `FEL_ALLOW_PRODUCTION=true`. FEL advierte que, en productivo, errores reiterados pueden consumir timbres; valida el catálogo fiscal y el XML en pruebas antes de usar datos reales. La clave de exportación 02 se rechaza hasta incorporar Comercio Exterior. La generación de CFDI de ingreso requiere que la fecha de factura sea la fecha local del día; Pagos 2.0 usa la fecha y los saldos del cobro registrado. Para cobros ligados a CFDI de ingreso PPD timbrados, `POST /api/billing/payments/{id}/prepare-payment-cfdi/` prepara un snapshot de saldos e IVA derivado del XML timbrado para el complemento 2.0, limitado a IVA 0/8/16 o exento; revisa el resumen antes de firmar; `POST /api/billing/fiscal-documents/{id}/generate-xml/` requiere `{"confirm_payment_snapshot":true}`, crea el CFDI tipo P con CSD protegido y valida el XSD CFDI 4.0 y el XSD Pagos 2.0 oficiales en local. El envío y consulta por referencia FEL usan las rutas `/send/` y `/query/`; antes de guardar la respuesta timbrada, el ERP coteja el importe, la forma de pago y los UUID relacionados. La primera versión limita cobros y facturas a MXN, IVA 0/8/16 o exento, sin retenciones. La documentación técnica está en el [portal oficial del SAT](https://wwwmat.sat.gob.mx/consultas/92764/comprobante-de-recepcion-de-pagos); los esquemas se conservan en `server/billing/fiscal/sat/` para validar sin conexión. El historial se consulta en `/api/billing/fiscal-documents/`.

El reporte `GET /api/billing/fiscal-documents/issued-register/?date_from=AAAA-MM-DD&date_to=AAAA-MM-DD` y la sección de Contabilidad muestran CFDI de ingreso tipo I y egreso tipo E timbrados, el UUID relacionado, impuestos separados por tipo, estado de cancelación y exportación CSV. Los totales provienen del XML guardado; el agregado suma documentos activos de ambos tipos, por lo que también separa ingresos y egresos. Los cancelados se muestran por separado. Es un registro operativo, no una declaración ni una conciliación con SAT, y no determina acreditabilidad de IVA. El reporte `GET /api/purchasing/supplier-bills/cfdi-register/?date_from=AAAA-MM-DD&date_to=AAAA-MM-DD` incluye XML de proveedores adjuntos, compara la huella y los importes con el registro privado, muestra impuestos por código/tasa y el estado de la cuenta por pagar, y permite exportar CSV desde Contabilidad. El impuesto se presenta como declarado en el XML; no se considera IVA acreditable y no se verifica criptográficamente el sello ni el estado del UUID en SAT/FEL.

La consulta `GET /api/billing/invoices/receivables-aging/?as_of=AAAA-MM-DD` reconstruye las cuentas por cobrar a la fecha elegida con las facturas abiertas antes del corte y los cobros aplicados hasta entonces, incluso si una factura aparece pagada actualmente. Agrupa el saldo por vencer, 1–30, 31–60, 61–90 y más de 90 días de atraso; separa las facturas sin fecha de vencimiento y ofrece detalle por cliente y folio. `GET /api/purchasing/supplier-bills/payables-aging/?as_of=AAAA-MM-DD` aplica el mismo criterio a facturas de proveedor registradas y pagos aplicados hasta el corte. Los reportes se basan en fechas de apertura/registro y aplicación almacenadas; no reconstruyen cancelaciones históricas ni sustituyen una conciliación bancaria. En la pantalla de Facturación, Ventas o Contabilidad con permiso de edición captura la fecha de vencimiento mientras la factura sigue en borrador; el sistema no asigna condiciones de crédito por su cuenta.

En **Facturación y cobros → Estado de cuenta por cliente**, Contabilidad, Gerencia o Ventas con permiso de consulta elige un cliente y fecha de corte. `GET /api/billing/invoices/customer-statement/?customer_id=<id>&as_of=AAAA-MM-DD` lista facturas abiertas a la fecha y cobros aplicados hasta el corte, con cargos, abonos y saldo acumulado. Un cobro aplicado a varias facturas aparece como una sola línea. Es un auxiliar interno de cuentas por cobrar: usa las facturas y aplicaciones registradas, incorpora las notas de crédito internas aplicadas, pero no anticipos sin aplicar ni cancelaciones históricas.

En **Compras → Estado de cuenta por proveedor**, Contabilidad o Gerencia con permiso de consulta elige un proveedor y fecha de corte. `GET /api/purchasing/supplier-bills/supplier-statement/?supplier_id=<id>&as_of=AAAA-MM-DD` lista las facturas registradas y pagos aplicados, con débito, crédito y saldo acumulado. Un pago aplicado a varias facturas aparece una sola vez. Es un auxiliar interno de cuentas por pagar y no representa una conciliación bancaria; no incluye devoluciones ni pagos no aplicados.

El CRM inicial registra y edita oportunidades desde `/api/opportunities/`, permite calificarlas con `POST /api/opportunities/{id}/qualify/` y cerrarlas como perdidas con `POST /api/opportunities/{id}/mark-lost/` (requiere motivo); una perdida se puede reabrir con `POST /api/opportunities/{id}/reopen/`. Las cotizaciones pueden guardar `opportunity` para mantener la relación comercial; al enviar la primera cotización la oportunidad avanza a “Cotización enviada” y al aprobarla queda ganada. La interfaz muestra el pipeline, permite asignar un responsable y cotizar desde oportunidades ligadas a un cliente existente. Las actividades de llamada, correo, reunión o tarea se programan en `/api/opportunity-activities/`, se pueden completar o cancelar y permanecen ligadas a la oportunidad. La portada muestra los seguimientos vencidos y los próximos siete días, y actualiza sus etiquetas de vencimiento cada minuto mientras está abierta; el panel permite abrir la oportunidad para completar o cancelar la actividad. Un prospecto puede guardarse antes de crear el cliente; `POST /api/opportunities/{id}/convert/` permite vincularlo con un cliente activo o crear uno con sus datos fiscales. La conversión detecta RFC repetido (o nombre y correo cuando no se captura RFC), reutiliza el cliente activo y bloquea coincidencias ambiguas o inactivas. Los cambios se anotan en la bitácora. `GET /api/opportunities/report/` resume oportunidades abiertas, importe esperado, ingreso ponderado por probabilidad y tasa de cierre, con desglose por origen; acepta `date_from` y `date_to` (AAAA-MM-DD) según fecha de creación. La tasa solo considera negocios ganados o perdidos. La pantalla de Oportunidades permite consultar el reporte y cambiar el periodo. Para enviar avisos por correo, configura `EMAIL_HOST`, `EMAIL_FROM` y los datos SMTP en `.env`; `python manage.py send_opportunity_activity_reminders --window-hours 24` avisa una vez antes de vencer y una vez cuando una actividad ya está vencida, dirigido al responsable activo o, si no existe, a quien la creó. La deduplicación queda registrada; en Docker Compose, activa `CRM_REMINDERS_ENABLED=true` para que el servicio `crm-reminders` ejecute sus tareas cada cinco minutos. Además de avisos de actividades, este servicio cambia a vencidas las cotizaciones enviadas cuya fecha límite ya pasó y registra el cambio en la bitácora. En DSM sin Compose se puede programar el comando desde el Programador de tareas. Los avisos dentro de la aplicación siguen disponibles aunque no se configure correo. La conciliación de oportunidades duplicadas aún está pendiente.

El libro contable inicial está disponible en `/api/accounting/accounts/`, `/api/accounting/journals/` y `/api/accounting/entries/`. Contabilidad puede preparar una póliza en borrador, contabilizarla con `POST /api/accounting/entries/{id}/post/` y revertirla con `POST /api/accounting/entries/{id}/reverse/`. El catálogo de cuentas y diarios empieza vacío; después de recibir el catálogo aprobado por el contador, Contabilidad puede dar de alta y activar cuentas y diarios en **Contabilidad → Catálogo contable y diarios**. Las mismas operaciones están disponibles en `/api/accounting/accounts/` y `/api/accounting/journals/`; los catálogos no se borran y el sistema protege cuentas con movimientos y diarios usados por pólizas. En **Contabilidad → Automatización de pólizas**, Contabilidad puede elegir cuentas y diarios activos para los cuatro eventos automáticos; la API correspondiente es `/api/accounting/posting-configurations/`. Con reglas activas, facturas y cobros de clientes, además de facturas y pagos de proveedores, crean pólizas **en borrador** para revisión; nunca se contabilizan automáticamente. Para proveedor, el contador define cuenta por pagar, cuenta de compra/inventario, cuenta para el impuesto declarado y diario de compras; para pago, cuenta por pagar, banco/caja y diario correspondiente. La cotización aprobada todavía no crea póliza.

La consulta `/api/accounting/reports/trial-balance/` muestra apertura, movimientos y cierre por periodo; `/api/accounting/reports/general-ledger/?account_code=1010` devuelve el detalle de una cuenta con pólizas contabilizadas y saldo acumulado; `/api/accounting/reports/financial-statements/` entrega estado de resultados y balance general. La pantalla de Contabilidad permite exportar como CSV la balanza, el mayor seleccionado y ambos estados financieros. Los reportes usan exclusivamente pólizas contabilizadas y aceptan `date_from` y `date_to` (AAAA-MM-DD). El estado de resultados usa los movimientos dentro del periodo; el balance general acumula saldos hasta la fecha final y presenta el resultado de ingresos/gastos aún no cerrado. La conciliación CxC/CxP `/api/accounting/reports/subledger-reconciliation/` compara los auxiliares con los códigos de cuentas de control indicados y una fecha de corte. La vista previa de saldos abiertos se envía como `multipart/form-data` a `POST /api/accounting/reports/open-items-preview/` con `file`, `as_of`, `receivables_account_code` y `payables_account_code`; usa la plantilla descargable desde Contabilidad. La vista previa informa errores y cuadratura sin crear registros. Si cuadra, Contabilidad puede preparar un lote con `POST /api/accounting/opening-balance-batches/prepare/` (`file`, `cutoff_date`, `receivables_account`, `payables_account`); otra persona con permiso puede publicar o rechazar mediante `POST /api/accounting/opening-balance-batches/{id}/review/`. La publicación crea únicamente saldos operativos, conserva el historial y no genera póliza ni habilita Pagos 2.0 para facturas sin historia fiscal verificada. Para la puesta en marcha, **Contabilidad → Balanza de comprobación → Importar saldos iniciales** acepta un CSV con columnas `Código`, `Cargo`, `Abono` y `Descripción` opcional; usa la [plantilla CSV](docs/plantilla-saldos-iniciales.csv). Prepara una única póliza general en borrador, requiere que cargos y abonos cuadren y no modifica saldos hasta que el contador la revise y contabilice. La fecha debe estar en un periodo abierto y se usan cuentas activas de movimiento. Contabilidad prepara meses en `/api/accounting/periods/`; cerrar un mes requiere que no queden pólizas borrador y bloquea la contabilización posterior en sus fechas. Reabrir requiere motivo y deja un evento inmutable con usuario y fecha. Son controles administrativos preliminares, no sustituyen el cierre fiscal ni la revisión del contador.

La conciliación está en `/api/accounting/bank-statements/`. Habilita `allow_reconciliation` únicamente en cuentas bancarias activas de tipo activo. La pantalla de Contabilidad importa un CSV con encabezados `fecha,referencia,descripcion,importe` (también acepta delimitador punto y coma), fecha `AAAA-MM-DD` e importe firmado (depósitos positivos, retiros negativos), junto con saldos inicial/final; el total debe cuadrar exactamente y no se permiten periodos que se traslapen para la misma cuenta bancaria. Para cada movimiento, la API propone líneas contabilizadas de la misma cuenta e importe/dirección, ordenadas por coincidencia de referencia y texto, y cercanía de fecha; devuelve los motivos de cada sugerencia. Este orden es heurístico y no confirma una coincidencia: Contabilidad revisa y confirma el vínculo. Además, la acción Vincular referencias exactas asocia en lote solo cuando referencia normalizada e importe/cuenta coinciden, la póliza está a no más de 3 días y el candidato es único; omite referencias repetidas o ambiguas y no contabiliza ni crea pólizas. Una línea contable solo se puede usar una vez. Si un movimiento no tiene póliza, Contabilidad puede preparar desde su fila una póliza balanceada en borrador: elige diario, cuenta de contrapartida y concepto; la cuenta bancaria se carga/abona según la dirección del movimiento. El ERP no la contabiliza: Contabilidad la revisa, contabiliza y después la vincula al estado importado. El vínculo conserva el folio y protege la fecha, la cuenta, el importe y la dirección de la línea bancaria; la contrapartida sigue editable mientras el borrador no se contabilice. `POST /api/accounting/bank-statements/{id}/prepare-adjustment/` recibe `line_id`, `journal`, `counterpart_account` y `memo`; reintentar sobre el mismo movimiento devuelve el borrador existente. El estado se cierra cuando todos los movimientos están vinculados, no hay diferencia y quedan registrados usuario/fecha. Los grupos Contabilidad y Gerencia tienen lectura; Contabilidad puede importar, asociar y cerrar.

Para crear el borrador de una póliza, envía al endpoint de entradas un diario, fecha, concepto y al menos dos líneas. Cada línea necesita una cuenta y un cargo o abono positivo; la suma debe quedar balanceada antes de contabilizar. La API valida esa condición y bloquea la edición posterior. Las reversiones crean una póliza nueva con los importes invertidos. Las pólizas originadas por cobros solo se revierten desde `/api/billing/payments/{id}/reverse/`, con motivo y confirmación; se conserva el historial y se recalcula el saldo del cliente.

El módulo **Soporte técnico** registra tickets en `/api/support/tickets/`; cada caso tiene cliente, asunto, descripción, prioridad, canal y responsable opcional, y puede ligarse a una orden de trabajo y a un equipo instalado serializado del mismo cliente. `GET /api/support/tickets/assets/?customer={id}` enumera solo equipos instalados de ese cliente; muestra fecha de instalación y garantía capturada en la ficha. Los estados se cambian con `POST /api/support/tickets/{id}/transition/`; los casos resueltos o cerrados pueden reabrirse y los cancelados quedan terminales. `POST /api/support/tickets/{id}/add-note/` registra notas internas por omisión; solo con el permiso `support.publish_supportticketmessage` y confirmación, Ventas, Gerencia y Operaciones pueden compartir una respuesta con el cliente. El enlace de seguimiento firmado se envía al correo registrado; vence en 30 días y se revoca al emitir otro. El correo del formulario debe coincidir con el guardado en la ficha. Las respuestas del cliente se separan de las notas del personal, quedan en la bitácora como cliente y reanudan casos en espera; las respuestas públicas del equipo dejan el caso en espera del cliente. Una bandeja de salida notifica al responsable o creador del ticket, reintenta errores SMTP hasta cinco veces y muestra su estado en la conversación. El portal no muestra notas internas ni datos del equipo. Se requiere `ERP_PUBLIC_URL` HTTPS y SMTP. El módulo permite configurar objetivos SLA opcionales por prioridad desde Django Admin; se congelan en el ticket, la resolución se pausa mientras espera al cliente y las respuestas públicas del personal registran la primera respuesta. No hay valores precargados hasta acordar tiempos con Redmagna. El SLA puede usar minutos corridos o un calendario semanal configurable con zona IANA; no admite feriados ni excepciones. La recepción opcional por IMAP requiere perfil Docker separado, servidor autenticador DMARC confiable, folio de ticket y correo registrado del cliente; consulta el buzón en modo de solo lectura, registra UIDVALIDITY/UID para evitar duplicados y solo procesa texto plano de hasta 4,000 caracteres, sin aceptar adjuntos. La primera etapa de Reparaciones se abre desde un ticket con equipo serializado instalado y conserva diagnóstico, propuesta, revisión manual de garantía, evidencia de autorización y transiciones auditadas; todavía no recibe equipos en taller, consume piezas ni crea cargos. Consulta [expedientes de reparación](docs/reparaciones-v1.md) y [soporte técnico](docs/soporte-tecnico-v1.md).

Los grupos iniciales son Administración, Ventas, Gerencia, Operaciones, Almacén, Compras y Contabilidad; el administrador asigna personas a grupos desde `/admin/`.

PostgreSQL guarda sus datos en `POSTGRES_DATA_PATH`; los archivos adjuntos privados viven en `MEDIA_PATH` y cada respaldo guarda un volcado, un archivo comprimido de medios y un manifiesto SHA-256 con el mismo sello. El servicio `db-restore-test` verifica la pareja y restaura el volcado en una base separada (`redmagna_restore_test`); falla si el hash no coincide o si la base ya existe. Los respaldos anteriores sin manifiesto se aceptan con aviso. SHA-256 detecta corrupción accidental, no cambios coordinados al respaldo y su manifiesto. Consulta la guía de Synology antes de restaurar. Mantén la primera instalación en la red local; para acceso remoto configura VPN o un proxy HTTPS y revisa las copias de seguridad del NAS. No expongas el puerto directamente a Internet.

Para permitir IVA al 8%, configura además `CFDI_BORDER_8_REVIEWED_POSTAL_CODES` con el código postal de expedición revisado por Contabilidad contra el catálogo SAT fronterizo. El servidor bloquea la preparación si el CP del emisor no aparece en esa lista. Esto no acredita por sí mismo el aviso SAT ni la elegibilidad del contribuyente.

## Límites actuales

- Al abrir directamente `dist/index.html`, la pantalla usa datos de demostración guardados en el navegador; para operar sobre la base central entra por el servidor en el NAS.
- El servicio aún no genera pólizas desde cotizaciones o CFDI ni importa movimientos bancarios de forma automática; la conciliación actual requiere CSV y asociación manual exacta. Las facturas/cobros de clientes y facturas/pagos de proveedores pueden crear borradores mediante reglas que Contabilidad configura en **Automatización de pólizas** y revisa antes de contabilizar. Los nuevos estados financieros son preliminares; faltan cierres contables, configuración revisada de cuentas y validación contra el contador. Tampoco incluye anticipos/saldos no aplicados, moneda extranjera, CFDI E para relaciones o condiciones distintas de la ruta inicial, devoluciones físicas, reembolsos y saldos a favor, reservas automáticas por cantidades cotizadas, lotes, costeo ni nómina. Las reservas manuales de material por orden de trabajo sí están disponibles; los conceptos de equipo/material aprobados y vinculados a un SKU aparecen como requerimientos en la orden y reducen el pronóstico de reabastecimiento. La API limita reservas y entregas a esos productos, ubicaciones y cantidades pendientes; las series exigen cantidades enteras. La demanda aún sin reservar se atribuye al almacén MAIN. El seguimiento serial identifica unidades y su ubicación/orden, pero aún requiere validación operativa con Almacén.
- Las facturas y cobros internos no sustituyen un CFDI timbrado. Ya se genera localmente el XML firmado de ingreso; el envío y timbrado FEL aún están pendientes de validar con sandbox.
- Los grupos iniciales controlan acciones de módulo; falta revisión con Redmagna de permisos por persona, cliente y proyecto.
- FEL Premium quedó confirmado como proveedor. La API consulta documentos enviados mediante `POST /api/billing/fiscal-documents/{id}/query/` y registra el evento. Antes de aceptar un timbre valida CFDI 4.0; para pagos también valida el XSD oficial Pagos 2.0 y coteja UUID, RFC, importes y CFDI relacionados. En todas las respuestas compara el contenido comercial/fiscal completo con el XML firmado enviado, permite solo el Timbre Fiscal Digital añadido por FEL y guarda la fecha exacta del timbre SAT. Una respuesta fallida, incompleta, discrepante o incierta no reenvía el comprobante. La cancelación tiene un flujo inicial con motivo SAT, UUID sustituto para motivo 01, confirmación explícita, acuse y estados pendiente/confirmado/rechazado. Antes de enviarla, el servidor abre el PFX, coteja el certificado y número SAT con el CSD embebido en el CFDI y comprueba que la llave privada corresponda al certificado; así evita enviar un PFX equivocado. Una consulta posterior a FEL puede actualizar el estado pendiente con el estatus del UUID. Está apagada por defecto y requiere habilitación explícita, credenciales FEL y PFX del CSD emisor. FEL informa que no hay sandbox de cancelación, y puede consumirse un timbre; la interfaz pide una confirmación final. La generación local no timbra por sí sola. `FEL_ENVIRONMENT` usa pruebas por defecto; producción requiere además `FEL_ALLOW_PRODUCTION=true`.
